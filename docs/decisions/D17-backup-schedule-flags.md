# D17: backup 명령 표면 재정의 — 수동 기본 + cron 셀프 등록 플래그

날짜: 2026-09-16
상태: 채택

## 맥락

backup 명령이 문서상 "cron 등록용 명령도 동일"로 안내되어, 일회성 수동 명령인지 자동
모드인지 표면이 모호했다. 또한 crontab 등록·확인이 셸 명령 조합에 의존해 진입 장벽이
있었고, help 명령 부재로 CLI 자체에서 사용법을 안내할 수 없었다.

## 결정

- `backup`(무옵션)은 **수동 1회 증분 백업**으로 의미를 확정한다.
- 자동화는 **cron 셀프 등록 관리 플래그**로 제공한다: `--schedule[=<크론식>]`(엔트리 등록,
  크론식 생략 시 `0 * * * *` 매시 정각, 5필드 사전 검증, 중복 방지), `--unschedule`(이
  도구의 엔트리만 제거), `--status`(등록 여부·등록 라인 확인). 실행 주체는 계속 cron이며
  도구는 crontab을 관리만 한다. 크론식 입력 지점이 명령 표면에 드러나야 한다는 사용자
  지적을 반영해 값 문법으로 노출했다.
- 전역 `help` 명령(-h/--help 동일)을 추가하고, 인자 오류 시의 짧은 usage와 분리한다.

## 근거와 대안

- **상주 데몬 모드(내장 타이머) 비채택**: 프로세스 생존(터미널 종료·재부팅·잠자기)을
  사용자가 책임져야 해서 시스템 스케줄러의 신뢰성을 포기하게 된다. FR-3("별도 데몬 모드
  없음")과 D16("cron 유지")과도 상충한다.
- **표기용 플래그만 추가하는 안 비채택**: 동작 차이 없는 구분은 가짜 구분이 된다.
- 등록 라인은 실행 시점의 작업 디렉토리와 `os.Executable()` **절대경로**를 인용 부호로
  감싸 생성한다. cron의 빈 PATH 환경에서도 동작하고, 운영 홈에서 실행하는 규율과 맞물린다.
- 엔트리 식별은 인용 부호를 제거한 라인의 `etl-worker backup` 포함 여부로 한다. 수기로
  등록했던 레거시 라인(`./etl-worker backup ...`)과 이 도구가 쓰는 인용 라인을 모두 잡는다.

## 영향

- internal/cli/schedule.go 신설(순수 라인 조작 함수 + crontab exec 래퍼 분리, 라인 조작은
  단위 테스트), backup 인자 파싱 확장(스케줄 플래그 상호 배타), main.go에 help 추가.
- crontab 쓰기는 macOS TCC 때문에 터미널 컨텍스트에서 실행해야 할 수 있다(에러 메시지에
  힌트 포함). 상세 배경은 [releases/v1.0.0.md](../releases/v1.0.0.md)의 TCC 절.
- 문서: README backup·스케줄링 절 갱신, [releases/v1.1.0.md](../releases/v1.1.0.md).
