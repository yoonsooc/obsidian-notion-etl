# M4 리뷰 (cron 등록과 무인 주기 실행)

기간: 2026-09-02 ~ 09-03 (설치·검증), 이후 1주 관찰
상태: **등록·무인 실행 검증 완료** (2026-09-03 00:15, 아래 검증 기록). 전체 디스크 접근
권한 부여 후 매분 스케줄로 실검증 → 매시 정각으로 복원. 완료 기준(무인 1주 무장애)은
2026-09-03부터 관찰로 판정

## 결정

- PRD §7대로 **cron 채택**, launchd는 v2 검토로 유지. 잠자기로 건너뛴 실행은 워터마크
  증분이 다음 실행에서 따라잡으므로 기능상 무해 (launchd의 이점은 놓친 작업의 기상 시 실행뿐)
- 스케줄: 매시 정각 (`0 * * * *`). 요약(stdout)은 logs/cron.log 누적, 상세는 실행별
  logs/backup/*.log. 변경분 없는 실행은 빈 로그 자동 삭제라 시간당 파일이 쌓이지 않음 —
  PRD의 "일자별 파일 분리" 취지를 실행별 파일 + 빈 로그 정리로 충족

## 사전 검증 (완료)

- **TCC/CloudStorage 쓰기 (핵심 리스크)**: 볼트가 ~/Library/CloudStorage(Google Drive) 하위라
  cron 컨텍스트의 쓰기가 TCC로 차단될 수 있음. 매분 touch하는 테스트 엔트리로 검증 →
  **cron에서 백업 디렉토리 쓰기 성공** (19:30:01 확인). 전체 디스크 접근 권한 추가 불필요
- backup 바이너리는 비대화형 실행에 문제없음 (환경 의존은 작업 디렉토리뿐, cd로 해결)

## 이슈: 세션(VSCode)에서 crontab 쓰기 차단 (원인 확정)

- 첫 crontab 쓰기(테스트 엔트리)는 성공했으나 이후 쓰기는 장시간 대기 후
  `crontab: tmp/tmp.NNNNN: Operation not permitted`로 실패 — macOS TCC가 VSCode 책임
  앱 컨텍스트의 /var/at 쓰기를 거부. 멈춘 것처럼 보인 root 프로세스들은 이 거부를
  기다리다 종료된 것 (현재 잔여 프로세스 없음)
- 부수 확인: setuid crontab은 세션 스크래치패드 경로를 읽지 못함(파일 방식은 /tmp 필요),
  CloudStorage 파일 rm이 동기화 지연으로 멈출 수 있음
- 결론: crontab 조작은 사용자 터미널(TCC 승인 가능한 앱)에서 수행

## 사용자 마무리 명령 (터미널에서 실행)

```bash
# 1) 매분 테스트 엔트리를 매시 정각 backup으로 교체 (권한 대화상자가 뜨면 허용)
echo '0 * * * * cd "<저장소 경로>" && ./etl-worker backup >> logs/cron.log 2>&1' | crontab -
crontab -l

# 2) 테스트 잔여물 정리
rm -f "<백업 디렉토리>/.cron-tcc-test"
rm -f "<저장소 경로>/logs/cron-test.log" /tmp/etl-crontab
```

## 추가 이슈: 첫 무인 실행이 exec 단계에서 TCC 블록 (2026-09-02 23:00, 원인 확정)

- 증상: cron.log가 0바이트로 생성되고 etl-worker가 CPU 0.00초·RSS 64KB로 무한 대기,
  워터마크 미전진. 매시 멈춘 프로세스 쌍이 누적됨 (수동 정리함)
- 진단: `sample`로 스택 확인 — **dyld의 getMainUnrealPath에서 블록**. Go 코드 진입 전,
  cron이 ~/Documents(TCC 보호 폴더)의 바이너리를 exec하는 순간 동의 대기에 걸림.
  cron은 UI가 없어 동의창을 못 띄우므로 영원히 대기
- 교훈: 사전 검증(touch)은 CloudStorage 쓰기만 증명했고, TCC는 폴더 범주별이라
  Documents의 **exec**은 별개 관문이었음. sh의 cron.log 생성이 성공한 것은 Apple
  플랫폼 바이너리 예외로 보임
- 해결: 시스템 설정 → 개인정보 보호 및 보안 → 전체 디스크 접근 → `/usr/sbin/cron` 추가
  (사용자 수행 필요). 대안은 launchd 사용자 에이전트 전환(동의창을 띄울 수 있는 컨텍스트) —
  v2 검토 사유에 이 문제가 추가됨

## 무인 실행 검증 (2026-09-03 00:15, 성공)

- 전체 디스크 접근 권한 부여 후, 빠른 확인을 위해 매분 스케줄로 임시 변경(사용자 요청)
- 첫 발화(00:15:00)에서 증분 백업 성공: 워터마크(09-01 18:42) 이후 수정분 2건
  (DN_260902, WG_260831~260906)을 정확히 미러링, 워터마크 00:15로 전진, 실패 0
- 검증 직후 매시 정각(`0 * * * *`)으로 복원. 이로써 cron 컨텍스트의 exec/네트워크/
  CloudStorage 쓰기/워터마크 갱신 전 구간이 무인으로 증명됨

## 운영 홈 분리와 권한 최소화 (2026-09-03, 사용자 결정: 전체 디스크 접근 권한 회수)

- 전체 디스크 접근 권한(FDA)이 필요했던 근본 원인은 프로젝트가 TCC 보호 폴더(~/Documents)
  안에 있었기 때문. 권한 회수를 위해 **운영 홈 분리** 적용:
  - `~/etl-worker/`(비보호 경로)에 바이너리 배포(go build -o) + 런타임 파일 일체
    (.env, base.config.yaml, configs/, logs/)를 **이동** (복사가 아님 — 워터마크 등 상태가
    두 곳으로 갈리는 것을 방지. 저장소에는 example 템플릿만 남아 실수 실행이 명확히 실패)
  - crontab을 `cd ~/etl-worker`로 전환, 수동 실행도 운영 홈에서
  - 남는 TCC 표면은 CloudStorage(볼트)뿐인데 cron에서 무허가 동작이 실측 확인됨
    → cron FDA 회수 가능
- 운영 홈 수동 백업 성공(워터마크 00:55 전진) → **01:00 cron 발화 성공**(증분 0건, 워터마크
  01:00 전진 — 새 경로의 cron 동작 확인, 이 시점은 FDA 유지 상태). 이후 사용자 FDA 회수,
  회수 후 발화 재검증 예정 (결과는 아래에 추가)
- 개발 워크플로 변화: 규칙 변경 시 저장소에서 빌드 후 `go build -o ~/etl-worker/etl-worker .`
  재배포 필요 (README에 명시)
